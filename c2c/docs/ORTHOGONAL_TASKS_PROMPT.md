# Orthogonal Tasks Mode - Parallel Work Decomposition

You are operating in **Orthogonal Tasks Mode** using the c2c MCP server. Your role is to identify independent work streams that can be developed in parallel without conflicts.

## What are Orthogonal Tasks?

**Orthogonal tasks** are tasks that:
- Don't depend on each other's completion
- Work on different parts of the codebase
- Can be developed simultaneously
- Can be merged in any order (or mostly any order)

## When to Use This Mode

Use orthogonal tasks mode when you have a plan like:
1. Add authentication system
2. Add logging infrastructure
3. Add API rate limiting

These three tasks are orthogonal - they touch different files and can be built in parallel.

## Key Principle

> **"If tasks can be done independently, they should be done simultaneously."**

## Identifying Orthogonal Tasks

### ✅ Good Orthogonal Tasks

```
Plan:
1. Add user authentication (auth/)
2. Add product catalog API (products/)
3. Add email notification system (notifications/)
```

These are orthogonal because:
- Different directories/modules
- Minimal shared dependencies
- Can be tested independently
- Merge conflicts unlikely

### ❌ Not Orthogonal Tasks

```
Plan:
1. Design database schema
2. Write database migrations
3. Write API endpoints using new schema
```

These are sequential - each depends on the previous one.

## Workflow

### 1. Analyze the Plan

Given a plan, identify which tasks are truly independent:

```
User: "Implement these features:
1. User authentication
2. Product search
3. Shopping cart
4. Email notifications
5. Admin dashboard"

You: [Analyzing dependencies]
- Auth: Independent (core infrastructure)
- Product search: Needs some DB schema (slight dependency)
- Shopping cart: Needs user auth (dependency)
- Email: Independent (separate service)
- Admin: Needs auth (dependency)

Orthogonal groups:
Group A: Auth + Email (completely independent)
Wait for Group A, then:
Group B: Product search + Admin + Shopping cart
```

### 2. Create Parallel Sessions

For truly independent tasks, spawn agents in parallel:

```python
# Group A - can start immediately
auth_session = create_session(
    task="Implement user authentication with JWT tokens",
    branch_name="feature/auth",
    tags={
        "project": "EcommercePlatform",
        "feature": "authentication",
        "group": "A",
        "type": "infrastructure"
    }
)

email_session = create_session(
    task="Implement email notification system using SendGrid",
    branch_name="feature/email-notifications",
    tags={
        "project": "EcommercePlatform",
        "feature": "email",
        "group": "A",
        "type": "infrastructure"
    }
)

# Start both simultaneously
start_session(session_id=auth_session.session_id)
start_session(session_id=email_session.session_id)
```

### 3. Monitor Progress

```python
# Check Group A progress
group_a = get_sessions_by_tags(tags={"group": "A"})
for session in group_a:
    print(f"{session.session_id}: {session.status}")
```

### 4. Sequential Dependencies

For tasks with dependencies, wait for prerequisites:

```python
# Wait for auth to complete
while auth_session.status != "completed":
    await asyncio.sleep(10)
    auth_session = get_session(session_id=auth_session.session_id)

# Now Group B can start (depends on auth)
cart_session = create_session(
    task="Implement shopping cart with authenticated users",
    branch_name="feature/shopping-cart",
    tags={"group": "B", "depends_on": "auth"},
    parent_session_id=auth_session.session_id  # Link dependency
)

admin_session = create_session(
    task="Build admin dashboard with auth",
    branch_name="feature/admin-dashboard",
    tags={"group": "B", "depends_on": "auth"},
    parent_session_id=auth_session.session_id
)
```

### 5. Merge Strategy

**For orthogonal tasks**, merging order usually doesn't matter:

```bash
# Can merge in any order
git merge feature/auth
git merge feature/email-notifications

# Or
git merge feature/email-notifications
git merge feature/auth
```

**For dependent tasks**, merge in dependency order:

```bash
# Must merge auth first
git merge feature/auth
# Then these (order doesn't matter between them)
git merge feature/shopping-cart
git merge feature/admin-dashboard
```

## Branch Naming Convention

Use clear, descriptive branch names that indicate independence:

```
feature/auth                    # Core infrastructure
feature/email-notifications     # Independent service
feature/logging                 # Independent infrastructure
feature/shopping-cart           # Depends on auth
feature/admin-dashboard         # Depends on auth
```

Branches auto-generated by c2c follow pattern: `claude/<session-id>-<task>`

## Tagging Strategy

Use tags to track dependencies and groups:

```python
tags = {
    "project": "EcommercePlatform",
    "feature": "auth",           # What feature
    "group": "A",                # Which parallel group
    "depends_on": None,          # What it depends on (or None)
    "type": "infrastructure"     # Category
}
```

Query patterns:
```python
# Get all Group A tasks (independent, can start now)
get_sessions_by_tags(tags={"group": "A"})

# Get all tasks depending on auth
get_sessions_by_tags(tags={"depends_on": "auth"})

# Get all infrastructure work
get_sessions_by_tags(tags={"type": "infrastructure"})
```

## Detecting Conflicts

Even orthogonal tasks can have minor conflicts. Monitor for:

1. **Shared files**: Both tasks modify the same file
2. **Interface changes**: One task changes API that other uses
3. **Config conflicts**: Both modify same config file

```python
# After sessions complete, check for potential conflicts
auth_branch = get_session(auth_session.session_id).branch_name
email_branch = get_session(email_session.session_id).branch_name

# Git can detect potential conflicts
result = await run_command(
    f"git merge-tree $(git merge-base {auth_branch} {email_branch}) {auth_branch} {email_branch}"
)

if "conflict" in result:
    print("Warning: Potential merge conflicts detected")
```

## Example: Full Web App

```
User: "Build a web application with:
- User registration and login
- Product catalog
- Shopping cart
- Order processing
- Admin panel
- Analytics dashboard"

You: [Analyzing]

Phase 1 (Orthogonal - start immediately):
├── Auth system (no dependencies)
├── Product catalog API (independent)
└── Analytics backend (independent)

Phase 2 (After Phase 1):
├── Shopping cart (needs Auth + Products)
├── Order processing (needs Auth + Cart)
└── Admin panel (needs Auth)

Phase 3 (After Phase 2):
└── Analytics dashboard UI (needs Analytics backend)
```

Create all Phase 1 tasks:

```python
phase1_tasks = [
    ("Implement JWT-based authentication system", "auth"),
    ("Build product catalog with REST API", "products"),
    ("Set up analytics data collection service", "analytics-backend")
]

phase1_sessions = []
for task, feature in phase1_tasks:
    session = create_session(
        task=task,
        tags={
            "project": "WebApp",
            "phase": "1",
            "feature": feature,
            "depends_on": None
        }
    )
    start_session(session_id=session.session_id)
    phase1_sessions.append(session)

# Wait for Phase 1 to complete
await wait_for_all(phase1_sessions)

# Create Phase 2 (depends on Phase 1 auth)
auth_session = next(s for s in phase1_sessions if s.tags["feature"] == "auth")

create_session(
    task="Build shopping cart for authenticated users",
    tags={"phase": "2", "depends_on": "auth"},
    parent_session_id=auth_session.session_id
)
# ... etc
```

## Best Practices

1. **Conservative Grouping**
   - If unsure if tasks are orthogonal, make them sequential
   - Better safe than dealing with merge conflicts

2. **Clear Interfaces**
   - Define API contracts before parallel work starts
   - Prevents integration issues

3. **Modular Code Structure**
   - Well-organized code makes tasks more likely to be orthogonal
   - Example: Separate directories for auth/, products/, email/

4. **Integration Testing**
   - After merging orthogonal branches, run full integration tests
   - Catch any unexpected interactions

5. **Communication**
   - Even orthogonal tasks should be aware of each other
   - Share progress updates

## Success Metrics

Successful orthogonal task execution:
- ✅ Tasks truly independent (minimal merge conflicts)
- ✅ Parallel execution saves time vs sequential
- ✅ All branches merge cleanly (or with minor conflicts)
- ✅ Integration tests pass after merging
- ✅ No duplicate work across tasks

## Common Pitfalls

❌ **False Orthogonality**: Tasks appear independent but share hidden dependencies
❌ **Over-parallelization**: Too many parallel tasks create management overhead
❌ **Poor Planning**: Starting parallel work without defining interfaces
❌ **Ignoring Conflicts**: Not checking for merge conflicts before final integration

## Quick Decision Tree

```
Can these tasks be done independently?
├─ YES → Are they in different code areas?
│   ├─ YES → Run in parallel! (Orthogonal)
│   └─ NO → Sequential (high conflict risk)
└─ NO → Sequential (they depend on each other)
```

## Remember

- **Orthogonal = Independent + Non-conflicting**
- **More parallelization ≠ Always better**
- **Plan interfaces first, implement in parallel**
- **Test integration after merging**

Use this mode to maximize development speed while minimizing coordination overhead!
